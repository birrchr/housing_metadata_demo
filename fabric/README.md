# Running the housing metadata model in Fabric

One pipeline run loads **one province-year**. Your scheduling tool calls the pipeline
with four parameters whenever a delivery lands. The pipeline itself has two activities:

```
pl_housing_load(source_system, reference_year, metadata_release, mode)
│
├─ Build staging    notebook nb_housing_build
│                   • reads Files/raw/year=<reference_year>/province=<source_system>/
│                   • maps and recodes it with the metadata release (housing_meta package)
│                   • appends the result to staging Delta tables (tagged with the run ID)
│                   • refreshes the Lakehouse SQL endpoint
│
└─ Load warehouse   stored procedure audit.usp_load_run      (only if the notebook succeeded)
                    • records QA results              → qa.check_summary / qa.check_detail
                    • blocking QA issue? → run FAILS, nothing published
                    • mode = validate  → stop here (status 'validated')
                    • mode = publish   → metadata history, dimensions, facts, wide table
```

Everything in [`bundle/`](bundle/) is generated by `housing-fabric bundle`. Regenerate it
rather than editing it by hand, so the pipeline, notebook and procedure stay in step.

| Parameter | Example | Meaning |
|---|---|---|
| `source_system` | `ON` | Province code; matches `province=XX` in `Files/raw` |
| `reference_year` | `2025` | Matches `year=YYYY` in `Files/raw` |
| `metadata_release` | `current` | `current`, or a folder under `Files/metadata/releases/` |
| `mode` | `validate` | `validate` runs QA only; `publish` runs QA, then loads the Warehouse |

## One-time setup

**1. Create the Fabric items** in your workspace:
- A Lakehouse named `lh_housing`.
- A Warehouse named `wh_housing`.

Other names work too: pass `--lakehouse-name` / `--warehouse-name` to every
`housing-fabric` command below.

**2. Build the package and upload it.**

```bash
uv build --wheel          # -> dist/housing_meta-0.2.0-py3-none-any.whl
```

Upload the wheel to `lh_housing` → `Files/lib/`.

**3. Upload the metadata.** Put the five CSVs from `metadata/` into
`Files/metadata/current/`. Approved snapshots go in `Files/metadata/releases/<name>/`
(see [Metadata releases](#metadata-releases)).

**4. Create the Warehouse objects.** In `wh_housing`, open a new SQL query and run these
in order:
1. `bundle/warehouse/01_tables.sql`
2. `bundle/warehouse/02_usp_load_run.sql`
3. `bundle/warehouse/03_views.sql`

**5. Import the notebook.** In the workspace, choose **Import → Notebook → From this
computer** and pick `bundle/nb_housing_build.ipynb`. Then open it and:
- Check the language is **Python**, not PySpark.
- Attach `lh_housing` as the **default Lakehouse**.
- If the Lakehouse has schemas enabled, change `TABLES_DIR` to `.../Tables/dbo`.

To check it, put one delivery in place (for example the sample
`data/raw/year=2025/province=ON/households.parquet` →
`Files/raw/year=2025/province=ON/`) and **Run all**. The output shows the staged row
counts and QA.

**6. Create the pipeline.** Collect four values:

| Value | Where to find it |
|---|---|
| Workspace ID | Workspace URL: `.../groups/<workspace-id>/...` |
| Notebook ID | Open the notebook: `.../synapsenotebooks/<notebook-id>` |
| Warehouse ID | Open the Warehouse: `.../datawarehouses/<warehouse-id>` |
| Warehouse SQL endpoint | Warehouse → Settings → SQL connection string (`xxxx.datawarehouse.fabric.microsoft.com`) |

Then pick one route:

```bash
# A. Create it through the REST API (needs: uv sync --extra fabric, and az login)
uv run housing-fabric deploy-pipeline --workspace-id <ws> --notebook-id <nb> \
    --warehouse-id <wh> --warehouse-endpoint <host>

# B. Generate the definition with your IDs filled in, then import it yourself
uv run housing-fabric bundle --workspace-id <ws> --notebook-id <nb> \
    --warehouse-id <wh> --warehouse-endpoint <host>
```

With route B, you have three ways to import:
- Send `bundle/requests/create_pipeline.json` as the body of
  `POST https://api.fabric.microsoft.com/v1/workspaces/<ws>/items` from any REST tool.
- Paste `bundle/pl_housing_load.DataPipeline/pipeline-content.json` into a new pipeline's
  JSON code view.
- Copy the `pl_housing_load.DataPipeline/` folder into a git-connected workspace folder
  and sync.

Then open the pipeline once and check that the **Load warehouse** activity shows
`wh_housing` as its connection. Fabric sometimes asks you to confirm or re-select the
connection on first open.

## Calling the pipeline from your tool

This is the only call your tool needs:

```http
POST https://api.fabric.microsoft.com/v1/workspaces/<ws>/items/<pipeline-id>/jobs/instances?jobType=Pipeline
Authorization: Bearer <token for https://api.fabric.microsoft.com>
Content-Type: application/json

{
  "executionData": {
    "parameters": {
      "source_system": "ON",
      "reference_year": 2025,
      "metadata_release": "current",
      "mode": "validate"
    }
  }
}
```

The response is `202 Accepted` with a `Location` header. Poll that URL until `status` is
`Completed`, `Failed` or `Cancelled`. On `Failed`, `failureReason` says why, for example
`1 blocking QA issue(s) in BC_2025. See qa.check_detail WHERE run_id = '...'`.

The same call from the command line (prints the job's final status, and exits non-zero
if the run failed):

```bash
uv run housing-fabric run --workspace-id <ws> --pipeline-id <pl> \
    --source-system ON --reference-year 2025 --mode validate
uv run housing-fabric run ... --dry-run     # just print the request
```

The token comes from `--token`, `$FABRIC_TOKEN`, or `azure-identity` (`az login`, or a
service principal through `AZURE_CLIENT_ID` / `AZURE_TENANT_ID` / `AZURE_CLIENT_SECRET`).

**Runs queue, they don't overlap.** The pipeline has `concurrency: 1`, so several
deliveries arriving together are processed one after another. That matters because each
run replaces its province-year in the Warehouse.

## Testing one province at a time

1. Upload `year=2025/province=ON/households.parquet` and run with
   `source_system=ON, reference_year=2025, mode=validate`. Expect `Completed`.
2. In `wh_housing`:
   ```sql
   SELECT * FROM audit.v_latest_runs;   -- ON 2025: validated
   SELECT * FROM qa.check_summary WHERE source_system = 'ON';
   ```
3. Run it again with `mode=publish`. Expect `Completed`, then:
   ```sql
   SELECT reference_year, source_system, value_label, COUNT(*) AS households
   FROM dw.v_record_labelled WHERE variable_id = 'TENURE'
   GROUP BY reference_year, source_system, value_label;
   ```
4. Upload BC 2025 and publish it. Expect **`Failed`**: the sample data has an unmapped
   tenure code `3`. `qa.check_detail` shows the exact value. This is the QA gate working.
5. Fix the metadata in `Files/metadata/current/`, as the walkthrough notebook does
   (`code.csv`: `TENURE,3,Other tenure,3,2025,`; `source_code_map.csv`:
   `BC,TENURE,3,3,2025,`), and publish BC again. Expect `Completed`.
   ON 2025 now shows in `qa.check_detail` as **`reload_recommended`**: the new TENURE code
   applies to ON's year too. Publish ON 2025 again to bring it up to date.

## Metadata releases

- Edit `Files/metadata/current/` and test with `metadata_release=current, mode=validate`.
- When the change is reviewed, copy `current/` to `releases/<name>/` (for example
  `2026-11-15_r1`) and publish with `metadata_release=<name>`. Release folders are
  never edited after that.
- Every publish versions the metadata in `meta.metadata_history`, so you can always see
  which mapping a published number was built with.
- When a release changes a row that applies to an already-published province-year,
  that run reports it as a **`reload_recommended`** warning (in `qa.check_detail`, one row
  per affected `dataset_id`). Publish those province-years again.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `No staged dataset XX_YYYY for run ...` | The SQL endpoint hadn't caught up. Check the notebook's `endpoint_refresh` output. The identity running the pipeline needs at least the Contributor role to call the refresh API |
| `no parquet files found ... for years={YYYY} provinces={'XX'}` | The file isn't at `Files/raw/year=YYYY/province=XX/*.parquet` |
| Notebook fails on `%pip install` | The wheel path in the settings cell doesn't match the file in `Files/lib/` (check the version number) |
| Staging tables show as "Unidentified" in the Lakehouse | `TABLES_DIR` doesn't match the Lakehouse type (schema-enabled needs `Tables/dbo`) |
| `notebookutils.runtime.context` is missing IDs | Seen when a service principal runs notebooks across workspaces. Set `WORKSPACE_ID` and `LAKEHOUSE_ID` in the settings cell |
| Run shows `Failed` with a QA message | Working as intended. See `qa.check_detail` for the run, fix the metadata, and run again |

## What has and hasn't been tested

- **Tested locally (`uv run pytest`):**
  - the one-province build and the Delta staging tables;
  - QA detection, and pruning of old staging runs;
  - that the parameter names agree across the pipeline, the notebook and the procedure's signature;
  - the pipeline create request, and the run request.
- **Not yet tested against a Fabric workspace:**
  - the Warehouse T-SQL;
  - the notebook's `notebookutils` calls;
  - the SQL endpoint refresh;
  - importing the pipeline and its Warehouse connection block.

  These follow Microsoft's current documentation. Expect to fix small things on the
  first deployment: start with step 5 (run the notebook by hand), then step 6.
