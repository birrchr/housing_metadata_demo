## 1. Purpose

Chris is introducing a **metadata-driven model** to his team for annual housing data
delivered by Canadian provinces (ON, BC, NS in the demo; MB used as a "new province"
example).

**The problem:** each province sends the same concepts (tenure, dwelling type, shelter
cost…) with different column names and code values, and those change year to year.
Historically this has been **heavily manual, spread out, and handled separately for
each province**.

**The idea:** all province-specific knowledge lives in **rows of metadata** (mapping
tables with `valid_from_year` / `valid_to_year`), and one generic load treats every
province the same. Yearly maintenance becomes editing a few reviewed rows, not
rewriting code.

**Goal of the repo:** a working demo plus explanatory material (notebook, slide deck,
README), and now a path to **production in Microsoft Fabric** with a Fabric Data
Warehouse as the final store.

## 5. The model (DuckDB, demo)

There are 8 tables in three groups:
- **Reference:** `codeset`, `code`, `variable`.
- **Mapping:** `source_column_map`, `source_code_map`.
- **Production:** `dataset`, `dataset_column`, `record_value` (long form: `source_value`
  plus canonical `value`, and `mapped_via` = `code_map` or `passthrough`).

How the rules work:
- **Validity:** one rule everywhere,
  `reference_year BETWEEN valid_from_year AND coalesce(valid_to_year, 9999)`.
- **Recoding:** if a province has any code-map rows for a variable in a year, its values
  are recoded through the map. If not, they pass through unchanged (NS already uses
  canonical codes).
- **Wide table:** `household_harmonised` is generated from `variable`.
- **QA views:** `v_qa_unmapped_columns`, `missing_variables`, `unmapped_values`,
  `invalid_codes`, `bad_numerics`, and `v_qa_summary`.

**Planted sample problems:** BC sends an extra `REGION_INTERNAL` column, and BC 2025 has
an unmapped tenure code `3`. A clean full build reports QA = `{unmapped_columns: 2,
unmapped_values: 1}`. These are expected.

**The walkthrough notebook's 2026 scenario:**
- ON renames `tenure_cd` → `tenure_code`.
- BC code `3` → a new canonical code `TENURE 3` "Other tenure", valid from 2025.
- MB joins with its own names and codes.

The fix is **24 metadata rows, 0 lines of Python**. The sample metadata is 70 rows in
total.

## 6. Decisions (and why)

| Decision | Reason / source |
|---|---|
| Production metadata is kept in **OneLake**, **not git**. The CSVs in `metadata/` are the demo stand-in | Chris: not clear codeset tables can go in git; production versions saved in OneLake |
| Present the data model as **a proposal / option**, not final | Chris expects the model to need tweaks |
| Fabric engine: **existing DuckDB build in a Fabric Python notebook → staging Delta in a Lakehouse → Warehouse stored procedure** | Chosen by Chris (reuses the tested code; same logic runs locally) |
| Warehouse shape: **star schema** | Chosen by Chris |
| Metadata maintained as **files in the Lakehouse** (`Files/metadata/current/`, approved snapshots in `Files/metadata/releases/<name>/`) | Chosen by Chris |
| **Design doc before code**, then implementation | Chosen by Chris |
| **One pipeline run = one province-year**, triggered whenever new data arrives; the pipeline must be **very lightweight and controlled by parameters** from Chris's calling tool | Chris's requirement |
| Pipeline = 2 activities only (notebook → stored procedure), `concurrency: 1` | Lightweight; runs queue instead of racing |
| Parameters: `source_system`, `reference_year`, `metadata_release` (default `current`), `mode` (`validate` / `publish`); `run_id = @pipeline().RunId` | |
| Blocking QA makes the procedure **THROW in both modes**, so the pipeline run is Failed and the caller sees why | No If/Fail activities needed |
| Blocking checks: `missing_variables`, `unmapped_values`, `invalid_codes`, `bad_numerics`. `unmapped_columns` only warns | No "ignore column" option exists yet |
| Dimensions are **type 1**; version history of all 5 metadata tables lives in one SCD2 table, `meta.metadata_history` (row_key + full row JSON as row_sig) | Generic, so new metadata tables or columns need no Warehouse change |
| Stale earlier years are **flagged** (`reload_recommended` in `qa.check_detail`), not auto-reloaded | One run handles exactly one province-year |
| Staging tables **append** to a `run_id` partition, with old runs pruned after 30 days | Runs never overwrite each other |
| The notebook refreshes the Lakehouse SQL endpoint via REST before the procedure runs | Metadata sync lag would otherwise make the Warehouse read stale staging data |
| Pipeline JSON, notebook and Warehouse SQL are **generated from one module** (`fabric_pipeline.py`); tests check parameter names agree | Prevents drift |

## 7. Fabric facts relied on

Checked against Microsoft Learn on 2026-11-09. Recheck before relying on them.

**Warehouse T-SQL**
- `MERGE` is GA. `IDENTITY` is supported, but must be `BIGINT IDENTITY` with no
  seed/increment, and values aren't sequential. `TRUNCATE` and `#temp` tables are supported.
- PK/FK/UNIQUE constraints are only allowed as `NONCLUSTERED … NOT ENFORCED`.
- No `nvarchar`/`nchar` (use UTF-8 `varchar`). `datetime2` max precision is 6. No triggers
  or materialised views.
- `ALTER TABLE` can only add nullable columns, drop columns, and add/drop constraints
  (`ALTER COLUMN` is in preview).

**Lakehouse SQL endpoint**
- String columns use the `Latin1_General_100_BIN2_UTF8` collation (case-sensitive).
- Metadata sync can lag behind writes. Fix: `POST /v1/workspaces/{ws}/sqlEndpoints/{id}/refreshMetadata`
  (long-running operation; `tables` scoped list, max 25; Contributor role or higher;
  service principals supported). Get the endpoint ID from
  `GET /lakehouses/{id}` → `properties.sqlEndpointProperties.id`.
- `sys.sp_dw_refresh_ext_table` works only if the endpoint was created with "new metadata
  sync" (preview) enabled.

**Pipelines**
- Definition part: `pipeline-content.json`. Created with `POST /v1/workspaces/{ws}/items`
  and `definition.parts` (base64), or updated with `/updateDefinition`.
- Activity types used: `TridentNotebook` (`notebookId`, `workspaceId`, `parameters`) and
  `SqlServerStoredProcedure` (`linkedService` type `DataWarehouse`: `endpoint`,
  `artifactId`, `workspaceId`).
- Run: `POST …/items/{id}/jobs/instances?jobType=Pipeline` with body
  `{"executionData":{"parameters":{…}}}` returns `202` plus `Location`. Poll until
  `Completed` / `Failed` / `Cancelled` / `Deduped`. The job API doesn't return the
  parameters a run was started with.

**Notebooks**
- `notebookutils.runtime.context` has `currentWorkspaceId`, and `defaultLakehouseId` when
  a default Lakehouse is attached. These can be missing under a service principal
  across workspaces, so the notebook has overrides.
- Python notebooks have unreliable `notebook.exit()` values. The design doesn't depend
  on them.
- Delta written outside `Tables/` (or `Tables/dbo/` in a schema-enabled Lakehouse) shows
  up as "Unidentified".

## 8. Environment gotchas (this machine)

- **DuckDB 2.0** renamed `fetch_arrow_table` → `to_arrow_table`. `staging._arrow()`
  handles both, because Fabric may have 1.x.
- The machine has ~7 GB RAM, and VS Code, Pylance and the R language server use most of
  it. One pytest run was **killed (exit 137)**. Tests use bounded DuckDB connections
  (`threads=2`, `memory_limit=1GB`).
- Jupyter execution via `nbconvert` takes ~4 minutes the first time (font cache).
- No `node`, so pptxgenjs can't be used; python-pptx is used instead. LibreOffice
  renders the theme `effectRef` as a shadow, so `build_deck.py` strips `p:style` from
  shapes.

**Known model limitations** (README table)
1. No "ignore column" mapping.
2. Recoded values are stored, so stale years must be reloaded.
3. Several files per province-year overwrite each other.
4. `UNPIVOT` drops NULLs.
5. No static check on mapping targets.
6. One grain / one key only.
7. No CI.
8. A build artifact `housing_meta.duckdb` is tracked in git.
